# Release the CLI

A release publishes packages other people install, so a maintainer starts it by hand and nothing merges into a release: core 0005, [releases are started by a maintainer through the pipeline](../../../docs/decisions/core/0005-releases-are-started-by-a-maintainer-through-the-pipeline.md), and core 0002, [a maintainer stays the last lever on agent work](../../../docs/decisions/core/0002-a-maintainer-stays-the-last-lever-on-agent-work.md). A bad release is fixed forward with a new one. How the jobs work is in `docs/PIPELINE.md`; this skill is the order of the steps and the traps.

## When the release needs a new library

A CLI change that uses new frodo-lib behaviour cannot be released before the library. The order, each step waiting for the one before:

1. Merge the library pull requests and release the library (the `release-the-lib` skill of [frodo-lib](https://github.com/rockcarver/frodo-lib/blob/main/.claude/skills/release-the-lib/SKILL.md)).
2. **Wait until npm shows the library version.** A fresh publish can sit in "Validating" for 25 minutes to about four hours; `npm view @rockcarver/frodo-lib dist-tags --json` moves when it is done.
3. Open the pin pull request ([pin-the-library](../pin-the-library/SKILL.md)); merge it when its checks pass.
4. Bring `main` into each CLI pull request that waited for the library, one at a time. Merge `main` into the branch with a merge commit and push that; never rebase and force-push the branch of someone else. A fork's branch is pushed to like any other when the maintainer has write access to the fork or the pull request allows edits by maintainers. The pipeline starts for the new head; a maintainer approves runs GitHub holds. Check against the published library, not a linked one: `npx tsc --noEmit` and the tests of the pull request.
5. Merge each pull request when its checks are green, one after the other. Two merges within a minute can fail the push run of the first commit for reasons that have nothing to do with the code; the run of the last commit is the one that counts.
6. Wait for the pipeline of the last commit on `main`, then release.

## Before you dispatch

- The pipeline run for the **last commit on `main`** passed: `gh run list -R rockcarver/frodo-cli --workflow pipeline.yml --branch main --limit 3`.
- **No release run is in progress, and nobody merges into `main` while one is.** The `Release` job commits the version and the changelog on top of the commit the run was dispatched from; a merge in between makes its push fail after the package is published (the first step of `npm-release` stops the run when `main` has moved, but not a merge during the last minutes). Check with `gh run list -R rockcarver/frodo-cli --workflow pipeline.yml --event workflow_dispatch --limit 3`, and tell everyone who can merge, other agent sessions included.
- You know which kind it is: `prerelease` (npm tag `next`), `premajor`, `patch`, `minor` or `major` (stable goes to `latest`, with a companion prerelease on `next`). After a change to `.github/workflows/pipeline.yml` itself, run a dry run first (`-f dry-run=true`: everything except the publish, the tag, the GitHub release and the Homebrew update).

## Dispatch

```console
gh workflow run pipeline.yml -R rockcarver/frodo-cli --ref main -f release-type=prerelease -f dry-run=false
gh run list -R rockcarver/frodo-cli --workflow pipeline.yml --event workflow_dispatch --limit 1
```

The run takes 10 to 15 minutes: build, tests, the live smoke test, the binaries for five platforms, `npm-release`, `Release`, the Homebrew update. Do not merge anything into `main` meanwhile.

## Verify

When every job succeeded:

- **npm:** `npm view @rockcarver/frodo-cli dist-tags --json`. A prerelease moves `next`, a stable release moves `latest` (and `next`). The publish log of `npm-release` says `+ @rockcarver/frodo-cli@<version>`; if the tag has not moved yet, that is the "Validating" hold, not a failure. Do not dispatch again.
- **GitHub:** `gh release view v<version> -R rockcarver/frodo-cli` shows a pre-release for a prerelease, with the five binary zips (`frodo-<os>-<arch>-<version>.zip`), `CHANGELOG.md`, `LICENSE` and `Release.txt`. `main` has the commit `Updated changelog and version for release v<version> [skip ci]`.
- **Homebrew:** both formulas are regenerated by every release (`docs/PIPELINE.md`, "Update Homebrew formulas"). In the tap, `Formula/frodo-cli-next.rb` names the new version; after a prerelease `Formula/frodo-cli.rb` must still name the latest stable release. The stable formula moves only with a stable release.

## When the run fails

- **Before `npm-release` published:** read the failed job, fix the cause, dispatch again. Nothing is left to clean up. The first step of `npm-release` ("Refuse to publish when the branch has moved") failing means `main` moved: dispatch again when nothing is being merged.
- **After `npm-release` published and a later job failed:** **never dispatch again.** The next version is computed from the latest tag, so the run would try to publish the same version, and npm refuses. "Re-run failed jobs" helps only when the failure was transient (a missing or expired `FRODO_CI_PAT` secret, a flaky step): it starts from the dispatched commit again, so a push rejected because `main` moved is rejected again. Then the release has to be completed by hand: frodo-lib's `PIPELINE.md` has the recipe it was done with ([The package is published but the Release job failed](https://github.com/rockcarver/frodo-lib/blob/main/PIPELINE.md)); the CLI also needs its binaries attached and the Homebrew update run, which that recipe does not cover, so ask the maintainer before you improvise.
- **Do not unpublish or delete a tag** unless the maintainer says so: `docs/PIPELINE.md` ("Recovering From A Bad Release") says how.

Stop and report when the maintainer's go is unclear. A fragment such as "cut a release and pin it" in a conversation is a note, not a go.
