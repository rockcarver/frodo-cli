# Build the native binary

The binary is the artifact users install: Node.js 26 with the CLI embedded as one file, built with `node --build-sea`. Why it is built this way, and the details per platform: "Binary packaging" in [docs/BUILD-ENV.md](../../../docs/BUILD-ENV.md) and [docs/PIPELINE.md](../../../docs/PIPELINE.md). You only need it to test packaging or startup, or to run the suite the way CI does. For everyday work the npm build is enough (see the `build-the-cli` skill).

## Build it locally

Needs **Node.js 26 or later**: `scripts/build-sea.mjs` stops with a clear message on an older Node, and `npm run build:only` is the build that works on any Node.

```console
npm ci
npm run build:binary           # build:only (tsdown + tsc), then build:sea
./dist-sea/frodo -v            # "You are running the binary release."
```

- `npm run build` is the same as `npm run build:binary`.
- `npm run build:sea` is the second half alone: it bundles `src/app.ts` into one file, `dist-sea/app.cjs` (`npm run build:sea-bundle`, config in `tsdown.sea.config.mts`), and embeds it in the Node runtime with `node --build-sea sea-config.json`.
- Output: `dist-sea/frodo` (`frodo.exe` on Windows), about 160 MB, and `dist-sea/app.cjs`. `dist-sea/` is gitignored.
- **macOS:** the build output is unsigned and the system kills an unsigned binary, so the script signs it ad hoc with the JIT entitlement. Check with `codesign -dv dist-sea/frodo` (it shows `Signature=adhoc`). That signature is only good for your machine.
- **Windows:** the script copies `frodo` to `frodo.exe`. **Linux:** no extra step.
- On an Intel Mac host `--build-sea` is broken upstream (BUILD-ENV.md); the release builds the Intel binary on an arm64 runner.

## Check the bundle is self-contained

The binary has no `node_modules`, so a package the bundler left as a bare `require("@...")` fails at run time, in the binary only. After any change to dependencies or to `tsdown.config.ts`, build fresh and expect `0` twice:

```console
npm run build:binary
grep -c 'require("@' dist/app.cjs dist-sea/app.cjs
```

A stale `dist-sea/` hides this problem (BUILD-ENV.md section 2.2.1), so rebuild before you check. The rule behind it: packages imported by shipped code go in `devDependencies` and `dependencies` stays empty (umbrella 0006, [published packages have no runtime dependencies](https://github.com/rockcarver/frodo/blob/main/docs/decisions/0006-published-packages-have-no-runtime-dependencies.md); `.github/instructions/dependencies.instructions.md`).

## Run the tests against the binary

```console
npm run test:binary                                   # the whole suite, what CI's Test job runs
npm run test:binary -- test/e2e/journey-list          # one file
```

`npm test` runs the same tests against `node dist/launch.cjs` through the shim in `test/e2e/shims/`, so most work never needs the binary. The scripts go through `tools/with-frodo-bin.mjs`, which builds `dist-sea/frodo` when it is missing and puts it first on `PATH`; `FRODO_TEST_BINARY=sea` selects it (resolution in `test/e2e/utils/FrodoBinary.cjs`).

- **A stale `dist-sea/frodo` is not rebuilt.** After changing `src/`, run `npm run build:binary` again, or you test old code.
- Do not rebuild `dist-sea/` or edit sources while a suite is running.
- The PTY tests default to the `dist/` build; only `FRODO_TEST_BINARY=sea` makes them use the binary.

## What the pipeline adds (maintainer-only)

**Do not try to reproduce these. A maintainer starts a release by hand and the pipeline does it** (umbrella 0005, [releases are started by a maintainer through the pipeline](https://github.com/rockcarver/frodo/blob/main/docs/decisions/0005-releases-are-started-by-a-maintainer-through-the-pipeline.md)). If a task asks you to cut a release or sign or publish a binary and you are a coding agent, stop and say so in the issue or pull request.

- Five binaries (linux-x64, linux-arm64, macos-arm64, macos-intel cross-built on an arm64 runner, windows-x64), each smoke-tested (`-v`, `journey -h`, `journey export -h`) and zipped.
- **macOS signing and notarization** with the organisation's Developer ID, using credentials only the pipeline holds. Local builds are ad-hoc signed only.
- npm trusted publishing, the GitHub release with the zips, and the Homebrew formulas, which install the prebuilt zips and are generated by `tools/update-homebrew-formula.mjs` (umbrella 0008, [Homebrew installs prebuilt release binaries](https://github.com/rockcarver/frodo/blob/main/docs/decisions/0008-homebrew-installs-prebuilt-release-binaries.md)). Nobody edits a formula by hand.
- On a pull request the pipeline builds the linux-x64 binary and runs the suite against it; that job is a required check.

## Verified, and not

Verified on macOS (arm64) with Node 26.5.0: `npm run build:binary`, `./dist-sea/frodo -v`, the ad-hoc signature, the zero count in the bundle check, and `npm run test:binary -- test/e2e/journey-list`. Not verified: Windows and Linux builds, Developer ID signing, notarization, anything the release does.
